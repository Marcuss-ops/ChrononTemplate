# Youtuberstle reference rebuild contract (2.5D correction)

## Shared delivery contract

- **Output:** native C++ authoring/assembly per named recipe in `tools/youtuber_style`; emit PNGs at 1920×1080 into `MP4/Youtuberstle/Final/<recipe>/` with source frame numbers.
- **Source and mapping:** directory names and filenames identify the supplied groups and frame spans (258 frames total), but are not by themselves evidence that the named recipe matches the visible subject. Audit each group from its actual reference frames before authoring; record any mismatch and use the visual sequence as the scene contract. Never map groups to recipes just by folder order.
- **Visual method:** the references are primarily 2.5D composites: raster or SVG-like artwork on image planes, with perspective/FOV, camera framing and parallax. Do not invent full 3D models. Build independently authored or GPT Image-generated visual assets from reference inspection, keep compatible scene elements on separate layers, and animate their plane transforms and the camera in C++/Chronon. The reference PNGs may be inspected as visual guides, but must not be cropped, traced pixel-by-pixel, pasted, or used as rendered source layers.
- **Timing:** preserve each reference run's frame-number span; compare first, middle, and last available frames. Static singleton shots remain static.
- **Composition:** reproduce each named folder's visible subject, layout, palette, on-screen text and motion. Use 16:9 composition, camera FOV/projection and per-plane depth only where the reference suggests it. Keep every essential element inside the frame.
- **Layers:** separate subject/photo/illustration, background, document/UI, text, highlight and glow where the evidence supports those layers. New assets may be imagegen raster assets or carefully authored SVG/vector assets. Keep RGB full plates as plates; do not treat them as transparent cutouts.
- **Must not appear:** reference pixels pasted into output, unrelated generated assets, generic stick figures, placeholder pages, fabricated text/UI, fake motion created by 1–2 pixel jitter, black/missing frames, or content outside frame bounds.
- **Acceptance evidence:** paired contact sheets for reference and render at first/middle/last frames for every named folder; 1920×1080 output/frame-count check; SSIM comparison on same-named reference/generated frames after resize (no crop); visual inspection of opening/middle/ending. SSIM is a comparison signal, not a substitute for visual review. Full reconstruction from reference-only material is expected to be visually faithful, not pixel-identical.

## Compatibility and limits

The original scene project/layers and source video are unavailable; the user has confirmed to proceed from the reference captures alone. Imagegen-created raster plates and C++-authored text/compositing approximate those visual ingredients, with the existing Blend2D pipeline providing 2.5D framing. Exact pixel identity is not possible from flattened references alone. The first v1 pass was rejected because of generic vector stand-ins. The revised v2 render contains 258 same-named 1920×1080 PNGs and scores mean SSIM 0.6182 over 58 unique opening/middle/ending samples (960×540; singleton scenes contribute one sample). This is a comparison signal, not approval by itself; the paired contact sheet is the visual review record. Remaining visible approximation is expected in scenes whose source artwork is highly stylized or whose original source video is unavailable.
